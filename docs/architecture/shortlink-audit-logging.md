# ShortLink Audit Logging

## Purpose

ShortLink changes and social publications are recorded in the generic MongoDB
audit collection `auditEvents`. The audit trail is intended to explain what
happened to a shortlink, who performed the action, and when it happened. It is
not part of the `ShortLink` entity and does not change public shortlink
resolution.

## Recorded Events

The BackOffice records these events for the `shortlink` entity:

| Event | When | Before | After | Metadata |
| --- | --- | --- | --- | --- |
| `shortlink.created` | A shortlink is successfully created | `null` | Created shortlink snapshot | None |
| `shortlink.updated` | A shortlink is successfully updated | Previous snapshot | Updated shortlink snapshot | None |
| `shortlink.deleted` | A shortlink is successfully deleted | Deleted shortlink snapshot | `null` | None |
| `shortlink.shared` | A social publication is attempted | `null` | `null` | Platform, message, success, provider error |

The snapshots are serialized JSON strings. They are deliberately generic so
the same audit infrastructure can be reused by other entities without making
the audit model depend on `ShortLink`.

## Audit Record

Each `AuditEvent` contains:

- `eventType`: event name, such as `shortlink.updated`.
- `entityType`: currently `shortlink` for this feature.
- `entityId`: the persisted shortlink identifier.
- `actorId`: the authenticated user or API-key identifier when available.
- `actorType`: `user` or `api_key`.
- `occurredAt`: UTC timestamp generated by the application.
- `beforeJson`: serialized state before the operation, when applicable.
- `afterJson`: serialized state after the operation, when applicable.
- `metadataJson`: event-specific data, including the social message and
  provider error details for sharing.

Social messages are stored in clear text in `metadataJson` by design. Access
to the MongoDB database and any future audit-reading endpoint must therefore
be treated as access to potentially sensitive content.

## Social Publication

The authenticated endpoint is:

```http
POST /api/shortlinks/{id}/share
```

Example request:

```json
{
  "platform": "telegram",
  "message": "Guarda il nuovo video"
}
```

Supported platforms are `telegram`, `discord`, and `facebook`. A user who can
view the shortlink can share it; the existing channel scope and shortlink
visibility checks still apply. The message belongs to this publication
request only and is never stored on the `ShortLink` entity.

On provider failure, the endpoint returns the provider error details and
records a `shortlink.shared` event with `success: false`. The audit failure
itself is logged through the application logger and does not make the main
shortlink operation fail.

## Operational Notes

- Audit records are stored in the MongoDB collection `auditEvents`.
- MongoDB and mock repositories are registered in the BackOffice composition
  root; mock scenarios initialize an empty audit collection.
- Audit persistence is best effort. Create, update, delete, and share do not
  roll back if audit persistence fails.
- Read-only logs are available from `GET /api/ShortLinks/{id}/logs` and
  `GET /api/User/{id}/logs`. User activity is available from
  `GET /api/User/{id}/activity-logs`; it filters by the user who performed the
  action and can include actions on other entities.
- All log lists are limited to the 50 most recent records.
- The application must not add credentials, tokens, or provider secrets to
  audit metadata or technical logs.
