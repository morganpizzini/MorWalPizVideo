# Shooting Range multi-tenant handoff

**Status:** Implemented in source and locally validated; not deployed. The
tenant-aware EF migration has not been applied to any SQL Server database.

## Outcome

Host multiple independently configured Range client deployments against one API
and one Azure SQL database, with each shooting range able to access only its
own accounts, bookings, settings, and other data. Operators provision tenants
through a management endpoint protected by a server-held key and callable
through Swagger.

**Assumptions:** One user account belongs to one tenant; identical usernames
may exist in different tenants. A client deployment identifies its tenant but
does not contain a secret. The user confirmed there is no existing data to
preserve, so the tenant schema can be initialized without a historical data
backfill. Verify that the target database is empty before resetting or
recreating its schema.

## Implemented Design

### Trust and request flow

1. Reuse the same client image for each App Service; set a validated runtime
   tenant slug per deployment, alongside its API URL. Include a single
   `X-Shooting-Range` header in every Range request, including CSRF, login and
   session restoration. The slug is public and is **only a selector**, never a
   credential. Fail visibly when runtime configuration is missing or invalid;
   never silently select a default tenant.
2. Before cookie authentication, resolve exactly one valid header to an active
   registry entry, storing its immutable internal tenant ID in a request-scoped
   context. Reject missing, duplicate, malformed, unknown or inactive tenants;
   use non-enumerating responses for unknown/inactive values. Do not resolve a
   tenant for CORS preflight, health probes, schema tooling, or the separately
   authenticated management/Swagger endpoints. No tenant context means no
   domain data access.
3. Login verifies the selected tenant's user credentials only. Persist tenant ID
   on both user and server-side session and include it in the protected cookie
   principal. On every request, compare selected tenant, cookie claim, persisted
   session and current user tenant, status, role and security version. Reject
   mismatches before domain operations; never trust a header, origin, role, or
   URL alone as authorization. Disabled tenants invalidate existing sessions.
4. Make domain endpoints deny-by-default. Only CSRF acquisition and login are
   anonymous tenant-selected endpoints; health and management have their own
   explicit policies. Close anonymous config, sessions, availability and public
   registration before multi-tenant exposure. Retain the current approved-user,
   admin-role, forced-password-change and CSRF protections. Decide ordinary-user
   onboarding before implementing the registration change.
5. Continue using the existing global write guard initially, including
   provisioning. It preserves current cross-instance transaction serialization;
   per-tenant locks are a separate optimization. Provisioning must not expose
   partially created tenants.

### Storage isolation

- Add a server-owned, immutable tenant ID to every tenant-owned relational row:
  configs, bays, mechanism types, exceptions, users, local sessions, bookings
  and threads. The tenant registry and singleton mutation guard are system
  records, not tenant data. Embedded whitelist IDs and message authors must
  refer to users in the same tenant.
- Parameterize EF Core global query filters by the current DbContext instance
  and request-scoped tenant ID, not a value captured when EF caches its model.
  No pooled context reuse without an independently verified reset strategy.
  Make non-request migration, readiness and provisioning access explicit and
  narrowly scoped; no generic request-path filter bypass. Query filters are
  defense in depth, not the sole write or authorization control.
- Derive ownership exclusively from the resolved server context. Never bind a
  tenant ID from JSON or allow it to be changed by replacement input. Audit
  tracked/local entities, inserts, updates, deletes, raw SQL, and future bulk
  operations. Load the target through a tenant-filtered query and update the
  tracked row with a tenant-qualified database predicate; reject absent or
  foreign IDs without revealing ownership. Ensure race-safe tenant ownership,
  including direct EF save paths, rather than relying on an ID-only `Update`.
- Keep existing globally unique row IDs and preserve existing foreign
  references. Replace the single `default` config ID assumption with exactly
  one config per tenant and unique IDs for new configurations; retain the
  existing ID for migrated data. Create tenant-qualified unique indexes for
  normalized username and mechanism name, plus one configuration per tenant.
  Add tenant-qualified relational constraints for booking-to-user/bay,
  session-to-user, thread-to-user and optional exception-to-bay. Initialize
  the schema with these constraints; validate embedded JSON references on all
  writes because SQL foreign keys cannot protect JSON.
  Include tenant ID in relevant query indexes. Prevent a cross-tenant ID
  collision from becoming a cross-tenant upsert.
- Update mock/in-memory paths, seeding, and test fixtures to use explicit
  tenant contexts. They must not be used as evidence for SQL constraints or
  independent-writer correctness.

### Tenant setup and Swagger

The management API creates a tenant with a unique, normalized slug,
display name and exact permitted client origin; initialize its configuration and
first administrator atomically. First-admin password is submitted only over
HTTPS in the request body, hashed with the existing password helper, never
returned or logged, and must be changed on first login. Repeat submissions must
not create duplicates or overwrite an administrator; return a clear conflict
or an idempotent result that contains no secrets. Do not add general
cross-tenant user administration or a public self-provisioning path.

This bootstrap endpoint **changes ADR-016's manual-first-admin decision** and
requires explicit approval. If not approved, provision the tenant only and
retain a documented, tenant-aware manual administrator insertion; do not
silently implement an alternative.

Use a dedicated strong management key supplied through protected API App
Service configuration or Key Vault, not the client or source. Authenticate it
with a dedicated management-only scheme and constant-time comparison; reject
missing/misconfigured keys, do not allow an ordinary tenant cookie as a
substitute, and never accept the key in URLs or log it. Support operational key
rotation, rate limiting, HTTPS, and restrict management ingress to trusted
operators. Redacted audit logs record successful and rejected provisioning
without passwords, keys or sensitive bodies.

The Range host currently has no Swagger setup or package. Add a supported
OpenAPI/Swagger UI integration scoped to this host, with an explicit management
security scheme so an authorized operator can enter the key through Swagger's
authorization control. Restrict access to the UI/document and endpoint at
trusted ingress; never embed a key in the UI or runtime JavaScript. Document
whether Swagger is enabled in the target environment and how operator access is
provided. Do not conflate access to Swagger itself with authorization of the
management operation.

### Browser, CORS and client configuration

- Configure an explicit allowlist of exact HTTPS client origins. The tenant
  registry owns the origin-to-tenant binding and the CORS decision must account
  for browser preflight, which does not include the actual tenant header value:
  allow preflight only for registered origins and headers, then check the
  origin-to-selected-tenant binding on the actual browser request. Non-browser
  callers cannot bypass authentication by forging Origin. Do not use wildcard
  credentialed CORS. Define exact local-development origins separately.
- All clients target the same API host, so the existing host-only auth cookie
  is shared across client origins in the same browser. Minimal initial behavior:
  one active Range session per browser/API host; a login to another tenant
  replaces the previous cookie, and a mismatched tenant is rejected and
  produces a clear reauthentication path. Do not sign out or revoke another
  tenant's session merely because a mismatched request arrives. Confirm this
  limitation with the user before implementation; simultaneous independent
  sessions require a deliberate tenant-aware cookie/antiforgery design.
- Serialize and escape runtime configuration safely in `server.mjs` rather
  than interpolating values into executable JavaScript. Supply consistent
  client and SSR configuration, verify hydration/direct navigation and
  development proxy behavior, and ensure the header is never sent to unrelated
  origins. No visual redesign is required.

## Risks

| Rank | Risk and affected surface | Mitigation and verification signal |
| --- | --- | --- |
| High | Forged header or cookie accesses another tenant. | Bind all four identities and deny anonymous domain reads; cross-tenant replay and admin tests fail safely. |
| High | Generic updates, JSON references or raw SQL cross tenant boundaries. | Server-owned IDs, tenant-qualified update and FKs, guarded JSON validation; SQL tests prove foreign-ID read/write and relationship rejection. |
| High | Unexpected deployed rows are discarded by a schema reset, or old writers omit tenant ownership. | Verify target row counts are zero before reset; quiesce/drain old instances and verify tenant constraints before rollout. |
| High | Management key compromises all tenants or leaks through Swagger/logs. | Dedicated key, secret storage, ingress restriction, rotation, redacted audit and negative management tests. |
| High | Existing public endpoints or public registration leak tenant information. | Complete authorization and onboarding decision before exposure; anonymous domain tests must fail. |
| Medium | Shared API-host cookie causes cross-tab sign-outs or confusing login switching. | Enforce mismatch rejection, document one active session; real-browser two-origin tests and product approval. |
| Medium | Global guard bottlenecks all tenants. | Retain correctness initially; monitor lock timeouts and defer per-tenant locking until separately designed and tested. |
| Medium | Unavailable persistent Data Protection, CORS or Swagger ingress blocks login/setup. | Verify actual Azure configuration, browser flows, scaling and operator access before release. |

## Implementation and Verification Status

### Implemented

- Each client deployment reads and validates `SHOOTING_RANGE`, exposes it
  through safely serialized `window.ENV`, and sends `X-Shooting-Range` on all
  API requests, including CSRF. Missing or malformed configuration fails
  closed.
- The API resolves an active tenant before cookie authentication. Active
  registry origins control exact credentialed CORS; preflight is resolved by
  origin and actual requests must match the selected tenant.
- All tenant-owned records use server-assigned `TenantId`. EF Core filters,
  composite uniqueness/foreign keys, write validation and tenant-scoped
  replacement logic prevent cross-tenant reads, relationship references and
  updates. Tenant identity is excluded from JSON input/output.
- Cookie claims and persisted sessions are tenant-bound. A selector/cookie
  mismatch is rejected without revoking the session belonging to the other
  tenant.
- Domain APIs use a deny-by-default authorization policy. Anonymous
  registration was removed; the manually provisioned first-administrator
  policy from ADR-016 remains. Provisioning does not create an administrator.
- `POST /api/shooting-range/management/tenants` uses the independent
  `X-Shooting-Range-Management-Key` authentication scheme, configured only
  on the API as `ShootingRange:ManagementKey` (App Service setting
  `ShootingRange__ManagementKey`). It creates the tenant and initial
  configuration. Swagger documents the management key when Swagger is
  enabled.
- EF migration
  `20261120233255_AddShootingRangeTenancy` and the model snapshot add tenant
  ownership and tenant-qualified constraints. The user confirmed no data
  needs preservation; no historical backfill was added. The migration has not
  been applied to a real SQL database.

## Testing Strategy

- **Unit:** slug normalization, malformed/multiple headers, missing context,
  immutable tenant ownership, key comparison and redacted errors.
- **API integration:** two tenants with same username and different credentials;
  login, every read and mutation, admin role, forced password change, revocation,
  disabled tenants, foreign ID and cookie/header replay; unauthorized requests
  never return foreign data or affect another tenant.
- **CSRF/CORS/security:** anonymous domain rejection, unauthenticated technical
  routes, exact origin preflight and actual origin/tenant matching, missing or
  invalid key, tenant cookie unable to invoke setup, setup key unable to access
  ordinary domain data, no secret disclosure; duplicate provisioning and
  missing management configuration fail closed.
- **SQL Server:** fresh-schema initialization against an empty database;
  tenant-scoped uniqueness, FK/JSON integrity and direct EF cross-tenant writes;
  same-tenant simultaneous booking and setup races preserve invariants; two
  tenants with independent slots behave correctly under the global guard.
  Existing in-memory tests are not a substitute.
- **Client:** runtime config, safe escaping and missing tenant; header on
  CSRF/login/reads/writes; existing credentials, errors and session handling;
  normal SSR/hydration and direct navigation.
- **End-to-end/release:** real browser with two independently configured
  origins and shared API cookies, tenant switching, preflight, CSRF, login,
  booking and admin actions; Swagger setup from trusted ingress; production-like
  Azure SQL migration, backup/restore and scaled session verification.

## Migration And Rollback

The user confirmed no existing data needs preservation. Before changing the
target database, verify its business tables are empty; if they are, prefer
initializing/recreating the schema with tenant ownership and constraints from
the start rather than adding a historical data backfill. If any unexpected
records exist, stop and obtain direction before discarding them. Pause traffic
and all old writers, drain instances, initialize the schema under operator
control, validate indexes, relationships and readiness, then deploy the
compatible API and all clients. Readiness must fail closed for incomplete
ownership or schema. There is **no safe mixed-version writer window** with the
current API.

Invalidate or expire legacy cookies/sessions and require fresh login; do not
implicitly assign them from an untrusted header. Provision the initial tenant
with the new deployment, verify it, then provision additional ranges. Once
tenant data has been written, rolling back to the old API would remove
isolation and must not be permitted; pause traffic and restore a verified
multi-tenant-capable version. Never run old code against the tenant-aware
database. Keep key rotation and exact client-origin rollback procedures
available without exposing key material.
